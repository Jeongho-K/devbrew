# 인터뷰 깊이 재설계 — Interview Brief

> 이 brief는 단독 완결 산출물이다. superpowers가 있으면 §7대로 brainstorming 해답공간으로
> 넘어가고, 없으면 이 brief 자체가 다음 단계의 입력이다. 텔레메트리는 `audit_file`에 있다.

## 0. 한눈에

**무엇** — spec-distill 플러그인의 Phase 1 인터뷰(`conducting-interview` skill. 사용자의 거친
요청 뒤에 있는 진짜 문제·원인·제약·대안을 캐내 다음 단계인 설계에 넘기는 단계)가 문제를
충분히 파기 전에 끝난다. 이것은 **두 번째 사이클**이다. 2026-07-20 사이클이 같은 증상을 받아
«집요함이 고정 라운드에 묶여 있다»로 진단하고 커버리지 원장(열어야 할 차원 다섯을 전부
닫아야 종료되는 장부)·teach-beat·blind-spot-prober 를 도입했는데, 그 결과가 여전히 얕다.

**왜 얕은가 — 이번에 확인한 것** — 첫 사이클 이후 인터뷰 9건의 원장 기록을 전수로 읽었다.
차원이 닫힌 근거는 9건 전부 «steelman 1회·blind-spot 1회·web sweep n회» 같은 이벤트
완료형이고, «무엇을 알게 되어 더 물을 것이 없다»는 내용 판단은 한 건도 없다. 정체를 잡으려던
coverage-mapper 의 «연속 3 probe 무진전» 트리거는 «진전 = evidence append» 정의 때문에 한
번도 발화하지 않았고(07-26 audit 원문), 첫 전이마다 돌아야 할 dispatch 규칙은 9건 중 4건에서
건너뛰어졌다. 사용자가 든 증상은 «질문이 안 떠올라 끝난다»다. 세션 기록에서 «되물었어야
했는데 되묻지 않은 자리»를 모델이 센 시도도 있었으나, 같은 계열 모델이 저자의 루브릭으로 셌고
사람이 검증하지 않아 그 결과는 방향의 근거에서 뗐다(C22). 사람이 대조한 사실 하나는 남는다 —
08-22 인터뷰 기록에서 추천안을 두 번 연속 수락한 직후 사용자가 «나 아직 뭐를 한다는지 명확히
이해가 안가»라고 말했다.

**진짜 문제 (재구성 v3, 사용자 동의·리뷰 후 재확인)** — **인터뷰어의 다음 행동이 사용자의
직전 답에서 나오지 않는다.** 답은 기록 대상이지 파고들 대상이 아니고, 그래서 «닫아도 되는가»를
판정할 재료가 애초에 생기지 않는다. 첫 사이클의 원장은 «무엇을 열 것인가»를 정했고 그것은
매번 채워졌다. 열린 차원 «안에서» 답을 파는 행동은 어떤 장치에도 걸리지 않았다. «질문이 안
떠올라 끝난다»는 이것과 같은 것이다 — 주의가 직전 답이 아니라 자기 목록에 가 있으면 목록이
끝날 때 떠오를 것도 없다.

**첫 사이클이 실패한 이유 (귀속)** — 셋이 맞물려 있다. 설계가 닫힘·dispatch·종료의 모든
결정을 인터뷰를 끝내고 싶은 그 턴의 재량에 두었고(설계), 그 재량이 규칙을 실제로 건너뛰었으며
— coverage-mapper 첫 전이 dispatch 4/9 미이행 — (미이행), 깊이를 재는 것이 아무것도 없어
«얕다»가 인상으로만 남았다(미측정). 첫 사이클의 steelman «더 무겁게 말고 더 가볍게»는
«집요함≠길이»로 방어됐는데, 그 방어의 그늘이 «답을 파고들지 않음»이었다.

**확정된 것** — 아래 §2 의 38항목은 종료 게이트에서 사용자가 전부 확정했다. 요지:
1차 지렛대는 «답 직후 그 답을 파고들기·그 전엔 닫지 않기 + 사후 측정(게이트 아님, 사람 검증
필수) + 닫힘 근거 노출»이고, 파고드는 수단은 «되묻기»와 «되비추기» 둘 다 후보다(C10·C23).
구조 추가(독립 판정 에이전트·probe 도구상자·재개방 전이)는 정당화가 필요한 **후보**다 — 어느
쪽인지는 설계가 비교한다(C17). 추천 답안은 항상 질문과 함께 먼저 낸다(C21). 질문을 묶어 묻는
형식은 제약이 아니라 후보이고(C24), 인터뷰어가 제시한 라운드·질문 수 허용치에 사용자가 ok 했으되 질문 수가
목적이 되지 않을지를 걱정했다(C5). seed 에는 «다시 검증하라» 표시를 넣고 무표시는 «미확인»이 기본이다(C29·C6).
Phase 0 은 첫 라운드에 native 워크트리를 만들고 브랜치를 rename(리뷰 근거로는 feature/* 로) 하며 audit 부터
커밋하며 한 브랜치에서 설계·계획·구현까지 간다(C7·C8·C26). 추천은 필요하되 트레이드오프를 보이게, 그리고 쉽게 이해되게 — 무엇을
결정하는지·용어·기술 사실·선택의 결과가 보여야 한다(C14·C33·C15). 외부 사례나 에이전트 추론을 사용자 요구로 승격하지 않고, 불확실한 것은
Open Question 으로 남기며 사용자의 중단·handoff 권리를 유지한다(C27·C28). 이전 답과 충돌하면 닫힌 주제도
다시 열되(C34) 그 «재개방 전이»를 어떤 장치로 구현할지는 후보다. seed 가 확정한 것은 다시 묻지 않고
흔들린 것만 재검증하며(C36), 성공은 질문 수가 아니라 §2 C35 의 조건으로 잰다.

**열려 있는 것** — §3 의 11건. 특히 파고들기의 판정자 형태(orchestrator 가 닫는 근거를 노출
vs 독립 에이전트의 거부권 — 후자는 «판정자의 입력을 피판정자가 쓴다»는 반박이 붙어 있다),
Phase 0 워크트리의 함정들(브랜치명 규칙·base branch·훅 경로·선커밋과 리뷰 훅·세션 고정과
state 경로), 어느 규칙을 산문에서 기계로 옮길지, 사후 측정을 사람이 어떻게 검증할지.

**다음 stage** — brainstorming 해답공간. 이 brief 가 문제공간의 종점이다. 설계는 두 방향(구조
추가 vs 지시 단일화)과 두 수단(되묻기 vs 되비추기)을 §4·§5 의 근거로 비교하되, 어느 쪽이든
«답 직후 그 답을 파고드는 행동»이 생기지 않으면 아무것도 바뀌지 않는다는 것이 이 인터뷰의
결론이다.

## 1. Goal · Non-goal

- **Goal** — 인터뷰가 사용자의 직전 답을 파고들게 만든다: 모호·피상·보류 답, 추천안 빠른 동의,
  근거 없는 확신, 새 정보에 대해 이유·사례·우선순위·상충·실패 조건을 확인하고, 그 전에는 차원을
  닫지 않는다. 수단은 «되묻기»(사용자에게 질문)와 «되비추기»(인터뷰어가 함의·위험·코드 사실을
  먼저 도출해 보여주기) 둘 다 후보다. 종료는 «이벤트가 한 번 일어났다»가 아니라 «더 물을 것이
  없다»에 근거가 붙어야 한다.
- **Goal** — 깊이를 사후에 잴 수 있게 한다 — 세션 기록에서 «파고들지 않은 자리»를 세는 방식으로.
  숫자는 사람이 읽고 자동 판정에는 쓰지 않으며, 모델이 센 값은 사람이 표본을 검증한 뒤에만
  근거가 된다. 다음 사이클이 «여전히 얕다»를 인상이 아니라 검증된 숫자로 말할 수 있어야 한다.
- **Goal** — 인터뷰의 질문·추천·트레이드오프가 사용자에게 쉽게 이해되게 전달된다: 무엇을
  결정하는지, 용어의 뜻, 기술 사실의 설명, 선택의 결과가 보인다.
- **Goal (경량)** — Phase 0 seed 가 «다시 검증하라» 항목을 표시하고(무표시=미확인), Phase 0 이
  첫 라운드에 워크트리를 만들어(브랜치는 feature/* 로) 인터뷰 자료부터 커밋한다.
- **Non-goal** — 질문 수·라운드 수를 늘리는 것 자체. 고정 체크리스트.
- **Non-goal** — 인터뷰가 설계·계획·구현의 결정을 미리 닫는 것. 접근법 비교는 brainstorming.
- **Non-goal** — 형식과 원장만 무거워지고 대화 깊이는 늘지 않는 해법.
- **Non-goal** — 인터뷰가 확정한 사실이 나중에 코드로 반증되는 층(brief 검증 쪽 문제). 형제
  워크트리 충돌 처분. (하류가 다시 물은 횟수를 세는 채널은 범위 밖 결정이 아니라 OQ2 로 열려 있다.)

트리거는 «진전 = evidence append» 정의 때문에 한 번도 발화하지 않았다(07-26 audit 원문).

닫힘 근거가 «1회 했다»인 것과 정합한다.

✎ **사용자 쪽 증상** — 08-22 인터뷰 기록에 추천안을 두 번 연속 수락한 직후의 사용자 발화가
있다: «나 아직 뭐를 한다는지 명확히 이해가 안가». C14·C15 의 «쉽게 이해되게»는 이 자리다.
분리 리뷰 둘이 «추천이 답 앞에 놓이는 것» 자체를 원인 후보로 올렸으나 사용자는 추천을 항상
먼저 두기로 했다(C21) — 그러므로 이 증상의 처방은 추천 시점이 아니라 그 뒤의 행동(파고들기·
되비추기·이해되게 전달)에서 나와야 한다.

✎ **Phase 0 ↔ Phase 1 경계 (seed 가 검증하라고 한 것)** — 인터뷰의 깊이는 seed 가 «무엇을
다시 검증하라»고 표시하는지에 상류로 의존한다(C6). 그 표시가 없으면 인터뷰는 확정을 다시
묻거나 열린 것을 확정으로 오독한다. 반대 방향의 위험도 있다 — 구조를 넣으면 에이전트 추론이
«확정» 라벨을 달고 넘어가는 경로가 되살아난다. 사용자가 고른 것은 «재검증 지시»(C29)와
«무표시=미확인»(C6)이고, 확정을 표시할지·표시 문법이 무엇인지는 OQ4 로 열려 있다.

## 3. Open Questions

- OQ1: 형제 워크트리(같은 리포에서 다른 세션이 쓰는 것)와 파일이 겹칠 때의 처분. 범위 밖으로

  필요한데, brainstorming 은 외부 플러그인이고 별 세션이라 지금은 셀 수 없다. 채널을 만들면
  외부 플러그인과 결합이 생긴다.
- OQ3: 되물음의 판정자 형태 — (가) orchestrator 가 «이 차원을 닫는 근거 한 줄»을 사용자에게
  노출 (나) 독립 read-only 에이전트의 닫힘 거부권과 그 판정 기록(S8 의 (다) 지표가 여기 딸린다) (다) 둘 다. (나)에는 «판정자의 입력을
  피판정자가 쓴다», «같은 계열 모델은 친숙한 텍스트를 선호한다», «후속 충분성 판정 에이전트를
  넣은 시스템이 인간 대비 유의차가 없었다»는 반박이 붙어 있다(§4).
- OQ4: seed 의 «재검증 지시» 표시의 구체 문법. Phase 0 의 억제 게이트(`check_seed.py`)가
  태그를 금지하므로 그것과의 관계도 미정.
- OQ5: Phase 0 워크트리 요구의 함정들 — 브랜치명 확정이 인터뷰 전에 «해답=구현»을 확정하는
  문제, 선커밋이 «턴 끝 전 커밋이 리뷰 훅을 끈다» 함정 위에 있는 문제, native 도구의 세션 고정과
  state 경로(main repo 고정)의 session-id 갈림. 리뷰가 더한 사실: native 도구는 worktree-*
  브랜치를 만들고(리포 규칙은 feature/*, project-init 이 검증) base 가 origin/HEAD 라 로컬
  미커밋 파일이 안 보이며, 훅 경로는 워크트리를 따라오지 않고, 종료 시 keep/remove 프롬프트에서
  잘못 누르면 브랜치째 사라진다. 사용자는 native 유지 + rename 을 택했고(C8·C12) 설계가 다룬다.
- OQ6: closed→open 재개방 전이를 허용하면 총량 바운드가 필요하다 — 현재 SKILL 은 «총량
  바운드는 이 판본에 없다»고 이월한 상태이고, 재개방 + derived 차원 되먹임 + 거부권이 합쳐지면
  상한 없는 루프가 된다.
- OQ7: 인터뷰가 확정한 사실이 나중에 코드로 반증되는 층 — 범위 밖(C16). 어느 사이클이 맡는지.
- OQ8: 어느 규칙을 산문에서 기계(스크립트·state 필드)로 옮길지. 현 SKILL 은 약 400줄 산문이고
  다중 턴에서 지시 준수가 단조 감소한다는 외부 근거가 있다. 리포 원칙(결정론은 보안·정확성
  게이트만)과 긴장한다.
- OQ9: teach-beat(각 질문 앞에 붙는 «이런 대안도 있는데 어떻게 보는가»류의 열린 질문)의 처분 —
  8건 전부 다지선다 뒤에 붙어 답 없이 소실됐고 인터뷰어도 회수하지 않았다.
- OQ10: 추천 답안·트레이드오프·«쉽게 이해되게 전달»의 형식. 사용자는 셋 다 필요하다고 했고
  추천이 답을 짧게 만든다는 것도 인정했다(C14·C33·C15).
- OQ11: 사후 측정의 방법 — 모델이 센 값을 사람이 어떤 표본으로 어떻게 검증하는지, 그리고
  «파고들었는가»만이 아니라 «그래서 새 정보를 얻었는가»를 어떻게 함께 재는지(리뷰 지적:
  행동 횟수만 세면 «evidence append = 진전»의 재현이 된다).

## 4. External Landscape

- GPT-4 인터뷰어의 결정적 결함이 「놀랍거나 모호한 답에 후속 질문하라」 지시 미이행이었고(해당 위반의 88%), 이를 트랜스크립트를 읽어 위반을 세는 방식으로 찾아냈다 «wuttke» — [취함] — 얕음이 한 문장으로 적히고 세어서 잡히는 결함이라는 근거. 단 그 계수는 사람 코더가 했다
- LLM 인터뷰어는 암묵 요구의 절반 미만만 끌어내고 유효한 질문은 후반 턴에 나온다 «llmrei» — [취함] — 일찍 닫으면 잃는 것이 바로 후반 질문이다
- LLM 인터뷰어의 종료 행동이 모델마다 크게 다르고 어떤 모델은 턴 예산을 항상 소진한다 «reqelicitgym» — [취함] — 종료를 모델 재량에 두면 너무 일찍 닫거나 끝없이 가거나 둘 중 하나
- Critical Decision Method 는 하나의 사건을 여러 pass 로 반복해 훑되 probe 를 lock-step 이 아니라 순간에 맞게 고른다 «cdm» — [중립] — 첫 사이클이 인용한 원형. 사건 회고용이라 설계 전 문제공간에는 절반이 대상을 잃는다는 반박이 있다
- ACTA 의 knowledge audit 은 전문성 항목마다 일반 probe 묶음(구체 사례·전형/이상·판단 근거)으로 세부를 캔다 «acta» — [중립] — C4 도구상자의 원형. 도메인 무관 질문이 요구 도출 실수 1위라는 반박이 붙는다
- 좋은 컨텍스트는 규칙 더미가 아니라 최소한의 고신호 토큰 + 표준 예시이고, 복잡성은 결과가 입증될 때만 더한다 «anthropic-context-eng» — [취함] — steelman 의 「단일 고고도 지시 + 예시」 근거
- 같은 계열 모델 judge 는 자기 출력 인식이 아니라 친숙한(저-perplexity) 텍스트를 선호한다 «judge-self-preference» — [피함] — 독립 판정 에이전트의 「독립」이 이름뿐일 수 있다는 반박
- 후속 질문이 충분한지 판정하는 분류 에이전트를 실제로 넣은 인터뷰 시스템이 인간 인터뷰어 대비 specificity·relevance 에 유의차가 없었다 «ainterviewer» — [피함] — 판정 구조가 깊이를 산 증거가 없다
- 지시를 쌓을수록 준수율이 비선형으로 붕괴하고 다중 턴에서 초기 지시 준수가 단조 감소한다 «instruction-stacking» — [취함] — 400줄 산문 SKILL 에서 「되물어라」가 묻히는 기전

## 5. 기각 · Blind Spots

- 기각 — 재구성 v2 가 함의한 해법 방향(독립 판정 에이전트에 닫힘 거부권 + probe 도구상자 + closed→open 재개방)을 주 방향으로 넘기는 것 → 원장 실측이 «답 직후 파고들기 부재»를 원인으로 가리켰고, 이 셋은 그 행동이 생기지 않으면 아무것도 바꾸지 못한다. 후보로 강등 — verdict: switched — ST1
- 기각 — 모델이 센 되묻음 누락 계수를 방향의 근거로 쓰는 것 → 같은 계열 모델 둘이 저자 루브릭으로 셌고 사람 검증 0건. 원래 / 재결정 / 근거: 계수를 v3 의 근거로 → 근거에서 떼고 brief·audit 에서 제거 → 판정자에 적용한 «동계열 선호» 비판이 계기에도 적용된다(분리 리뷰)
- 기각 — 추천 답안을 사용자가 먼저 한 줄 쓴 뒤에 보이는 «추천 지연» → 분리 리뷰 둘이 앵커링 근거로 후보에 올렸으나 사용자가 «추천은 항상 먼저»로 방어했다(C21). 근거는 §4 «anchoring-delay» 에 남긴다
- 기각 — 답 단위 판정자 = 사용자(매 답에 «더 팔 축» 선택지) → 분리 리뷰가 OQ3 의 이분법을 깨는 후보로 올렸으나 사용자가 채택하지 않았다(C25) — 라운드당 클릭 증가
- 기각 — «묶어 묻기»를 제약으로 고정하는 것 → 사용자 원문은 한 라운드에 하나씩만 묻고 묶이지 않는 것을 가리켰다고 말했을 뿐 묶음이 더 깊다고 말하지 않았고, 하류 설계 도구는 반대 선택을 했다. 후보로 강등(C24)
- 기각 — 깊이 지표 (다) «독립 에이전트의 판정 기록» → S8 에서 (나)와 함께 선택됐으나, 독립 판정자 자체가 후보로 강등되면서(C10) 그 기록도 후보 지위가 됐다. OQ3 의 (나)에 딸린다
- 기각 — seed 무표시 = 사용자 확정 → 표시 누락(구버전·실수)이 확정으로 승격된다. 원래 / 재결정 / 근거: 무표시=확정 → 무표시=미확인 → 현행 Phase 1 의 provisional 기본값과 정합, fail-closed(codex)
- 기각 — native 워크트리 도구를 그대로 쓰는 것 → 그것이 만드는 worktree-* 브랜치가 리포 규칙(feature/*)과 충돌. 원래 / 재결정 / 근거: native 우선 → native 유지 + feature/* 로 rename → 브랜치명 검증기가 거부한다(분리 리뷰, 공식 문서)
- 기각 — 깊이 지표 «하류 brainstorming 이 brief 를 읽고 다시 물은 횟수» → Round 2 에서 제안·선택됐으나 측정 채널이 없다(brainstorming 은 외부 플러그인·별 세션). 게이트가 되면 인터뷰가 설계 결정을 brief 에 선기입하는 쪽으로 왜곡된다. OQ2
- 기각 — «지표는 사용자 육안만» → Round 4 의 빠른 답. 되물음에 «재고 가능»으로 답했고 사후 측정(게이트 아님)을 받아들였다. 원래 / 재결정 / 근거: 육안만 → 측정만·게이트 아님 → 첫 사이클이 육안(V9)뿐이라 얕음이 인상으로 남았다
- 기각 — seed 의 «세션에 워크트리가 고정되지는 않게» → Phase 0 에서 뜻이 미확인이었고 Round 3 에서 사용자가 철회했다. 원래 / 재결정 / 근거: 고정 안 되게 → native 도구(세션 고정)로 → 사용자가 대가를 알고 골랐다
- 기각 — 얕음의 구체 사례를 사용자에게 묻는 것 → «잘 모르겠네». 대신 아카이브 원장 9건을 전수로 읽어 닫힘 근거의 모양을 확정했다
- 기각 — 첫 사이클 실패의 귀속을 사용자 직감으로 정하는 것 → «모름». 아카이브 원장 행 실측으로 셋(설계·미이행·미측정)이 맞물려 있음을 확인했다
- 위험 — 숨은 가정: 독립 판정자가 닫힘을 거부하면 인터뷰가 깊어진다. 거부는 «다시 물어라»만 만들지 «무엇을 물어라»는 못 만들고, 같은 계열 모델의 자기교정은 1회 뒤 급격히 수확 체감한다. 거부권이 만드는 것은 evidence 를 한 번 더 붙여 판정자를 통과시키는 형식적 재질문일 수 있다 — 적대적 premortem
- 위험 — 숨은 가정: 판정 분리가 tools allowlist 로 성립한다. subagent 는 부모 대화를 못 보고 orchestrator 가 쓴 프롬프트만 받으므로 판정자의 입력을 피판정자가 쓴다. fork 는 같은 컨텍스트라 같은 전제다. 둘 다 «판정 위치 이동»이지 분리가 아니다 — 적대적 premortem
- 위험 — 숨은 가정: 두 번째 사이클이 첫 사이클과 다른 층을 건드린다. 함의된 해법 넷은 전부 orchestration 상태기계 층이고 첫 사이클도 같은 층을 바꿨다. 새 판정자의 기준이 다시 산문이면 이행률 미측정을 재생산하고, 결정론으로 만들면 하니스 가볍게 원칙과 충돌한다 — 적대적 premortem
- 위험 — 숨은 가정: CDM/ACTA 식 도구상자가 «안 떠올라 끝남»을 해결한다. CDM 은 이미 일어난 사건 회고용이라 설계 전 문제공간에는 절반이 대상을 잃고, 사용 횟수가 원장 evidence 로 적히는 순간 체크리스트로 퇴화한다 — 적대적 premortem
- 위험 — 숨은 가정: Phase 0 워크트리 요구가 깊이와 무관한 무해한 짐이다. 브랜치명과 «구현으로 갈 요청» 판정을 Phase 0 이 내리면 인터뷰 전에 «해답=구현»이 확정돼 사용자 자신의 제약(하류 결정 선점 금지)의 첫 위반이 Phase 0 이 된다. 선커밋은 «턴 끝 전 커밋이 리뷰 훅을 끈다» 함정 위에 있고, native 세션 고정은 state 경로(main repo 고정)와의 session-id 갈림 표면을 늘린다. 현행 framing-requests SKILL 에는 git·워크트리 언급이 0건이다 — 적대적 premortem. 사용자는 유지를 택했다(C12)
- 위험 — 실패 양식: 종료 시 사용자 일괄 확인이 클릭 한 번으로 통과돼 override 가 default 경로가 된다. 07-26 인터뷰의 «사용자 미응답 → 보류 → closed»가 이미 이 경로다 — 적대적 premortem
- 위험 — 실패 양식: 재개방 전이 + 총량 바운드 부재 + 판정자 거부권이 합쳐져 상한 없는 루프가 된다. «10~15 라운드 허용»은 사용자 인내의 상한이지 루프의 상한이 아니다 — 적대적 premortem
- 위험 — 실패 양식: 확정 사실이 틀린 채 «깊게» 파인다. 되묻기·도구상자·재개방은 질문 수와 차원을 다루지 brief 의 확정 사실 검증을 다루지 않는다 — 적대적 premortem. 범위 밖으로 둠(C16), OQ7
- 위험 — 실패 양식: Phase 0 선커밋·워크트리가 리뷰 훅과 state 를 조용히 끊는다 — 어느 쪽도 소리를 내지 않는다 — 적대적 premortem
- 위험 — 실패 양식: 사후 측정이 게이트가 되는 순간 질문 수 늘리기로 왜곡된다(Goodhart). 사용자 우려와 같다 — steelman
- 위험 — 실패 양식: 되묻기를 «질문 더»로 구현하면 첫 사이클이 방어만 하고 반증하지 못한 fatigue 반박이 다시 열리고, 동의 편향(추천 빠른 동의)이 함께 오른다 — 분리 리뷰
- 위험 — 숨은 가정: 파고들기 행동 횟수를 세면 깊이가 잡힌다. 그 질문이 새 정보를 얻었는지는 별개의 측정이고, 안 재면 «evidence append = 진전»이 «이유를 한 번 물음 = 진전»으로 재현된다 — 분리 리뷰(codex)
- 위험 — 숨은 가정: «단일 강한 지시»만으로 충분하다. Wuttke 의 결과 자체가 «단일 지시가 안 지켜졌다»이므로 지시만으로 충분하다는 증거는 없다 — steelman 자신의 caveat. 그래서 결론은 «측정 전엔 어느 구조도 정당화되지 않는다»이지 «구조 0»이 아니다

  > spec-distill 의 Phase 1 interview 가 문제를 충분히 파기 전에 끝난다. 커버리지 원장이 있는데도 실제 사용감은 라운드마다 질문을 소진하고 나면 끝나는 쪽이다. 질문 수나 고정 체크리스트를 늘리는 방식이 아니라, 왜 얕게 끝나는지 현재 구현과 변경 이력에서 먼저 원인을 찾아 설명하고, 가능한 재설계 방향을 비교한 뒤, 더 집요한 문제공간 탐색으로 재설계해 구현까지 가라. 사용자는 이 방향 자체가 좋은 방향이 아니라면 그렇게 말하라고 했다 — 아래의 방향 서술도 검증 대상이다.
  >
  > Phase 0 은 이미 있는 request-framing skill 이고 Phase 1 은 conducting-interview skill 이다 — 이 seed 자체가 request-framing 이 만든 것이고, 다음 세션의 인터뷰는 바로 그 개선 대상 skill 로 돈다. Phase 0 착안: 그 자기참조는 쓸 수 있는 자료이고, 이번 인터뷰의 라운드 기록도 대조 코퍼스에 넣을 수 있다.
  >
  > 이 문제는 두 번째 사이클이다. 2026-07-20 인터뷰(지금은 archive 에 있다)가 같은 요청 — 더 집요하게, 미지를 드러내 가르치고, 외부 탐색을 더 — 을 받아 «집요함이 고정 라운드에 묶여 있다»로 재구성했고, 그 결과가 커버리지 원장·teach-beat·blind-spot-prober·floor 다섯 차원(root_problem·landscape·skepticism·blind_spot·open_questions)이다. 그때 steelman 은 «더 무겁게 하지 말고 더 가볍게»였고 집요함은 길이가 아니라고 재정의해 방어됐다. 그 결과가 여전히 얕다는 것이 이번 발단이다. 전부 재검토 대상이다. 다만 그때 무엇을 고민했고 왜 그렇게 정했는지를 그 brief·설계·CHANGELOG 에서 먼저 이해한 뒤 재구성하라. Phase 0 제안: 같은 결론으로 돌아온다면 첫 사이클이 왜 얕았는지를 설명할 수 있어야 한다.
  >
  > Phase 0 이 구현을 읽고 본 원인 후보다. 검증 대상이지 확정이 아니다. 종료 술어가 이벤트 완료다 — landscape 는 sweep 한 번, skepticism 은 verdict 한 건, blind_spot 은 dispatch 한 번이면 닫힐 수 있고 게이트는 상태 토큰과 evidence 비어있지 않음만 본다. 진전의 정의가 evidence append 라 피상적 답도 진전으로 센다. 4-block 이 질문 하나와 추천 답안을 강제해 라운드당 결정 하나, 추천안 동의를 유도한다. closed 에서 open 으로 돌아가는 전이가 없다. derived 차원의 공급원이 coverage-mapper 뿐이고 seed 에서 주제 차원을 처음에 뽑을 의무가 없다. Phase 0 이 찾은 과거 사례 셋: 사용자 침묵으로 open_questions 를 닫은 것(docs/archive/interview/2026-07-26-qg-impact-driven-qa-runtime-interview.md 의 원장), 묻지 못한 채 끝낸 것(docs/archive/interview/2026-07-25-spec-distill-brief-handoff-redesign-interview.audit.md 의 원장), 확정 사실이 코드로 반증된 것(docs/superpowers/specs/2026-09-02-seam-channel-verification-design.md 의 «brief 의 사실 하나가 코드에 의해 반증됐다» 절). 규칙 대부분이 SKILL 산문인데 orchestrator 가 그것을 얼마나 이행하는지의 측정 기록을 Phase 0 은 찾지 못했다.
  >
  > 방향은 이렇다. 인터뷰는 고정 라운드나 질문 수가 아니라 문제공간의 충족도로 진행한다. 모호하거나 피상적인 답, 추천안에 대한 빠른 동의, 근거 없는 확신 하나로 차원을 닫지 말고 필요하면 이유·사례·우선순위·상충 관계·실패 조건을 후속으로 확인한다. 새 답이나 외부 근거가 이전 답과 충돌하면 이미 닫힌 주제도 다시 연다. 외부 탐색은 실제 도메인의 대안과 prior art, 현재 결정에 영향을 주는 사실 검증에 쓴다 — 모델의 낡은 지식이 방향을 고정하지 않게 하되, 외부 사례나 에이전트 추론을 사용자 요구로 승격하지 않는다. 기존 4-block 형식, floor 와 derived 커버리지, 상태 전이, probe 와 round 개념, 종료 조건, steelman 과 blind-spot 결과의 후속 질문 반영을 전부 점검하되 무엇을 유지하고 바꿀지 미리 단정하지 말고 여러 접근을 비교하라. 형식과 원장만 무거워지고 실제 대화 깊이는 늘지 않는 해법은 피한다. 라운드·dispatch·web·codex 비용은 늘어도 된다(사용자 확인) — 다만 과거 사례를 찾는 탐색은 «너무 비용 많이 들지 않게». 질문을 한 번에 하나만 하는 원칙은 푼다 — 대체 방식은 네가 정하되, 사용자는 Phase 0(framing-requests) 쪽이 더 좋아 보인다고 했다. 추천 답안을 유지할지도 네 판단이다.
  >
  > 성공한 인터뷰는 질문을 많이 한 인터뷰가 아니다. 핵심 방향이 사용자 표현과 근거로 충분히 드러나고, 중요한 가정과 상충 관계가 검토되고, topic-specific 미탐색 영역이 남지 않았는지 확인되고, 불확실한 것은 억지로 닫지 않고 Open Question 으로 남기고, 사용자가 중단하거나 handoff 를 고를 권리가 유지되며, 최종 brief 만 읽은 brainstorming 이 문제를 다시 추측하거나 같은 질문을 반복하지 않는다. 역할 분담은 유지한다(사용자 확인): 인터뷰는 조사와 문제공간, brainstorming 은 설계, writing-plans 는 계획, 그 다음이 구현이다 — 인터뷰의 조사가 설계 입력으로 충분해지면 되고, 접근법 비교는 brainstorming 의 몫으로 남는다. Phase 0 관찰 하나: «미탐색 영역이 남지 않았다»는 그 자체로는 증명할 수 없어 대리 조건이 필요할 수 있다.
  >
  > 경계는 이렇다. request-framing 은 다음 에이전트에게 무엇을 맡길지 정렬해 interview-seed 를 만들고, interview 는 그 요청 뒤에서 실제로 해결해야 할 문제·원인·제약·이해관계·대안과 방향을 탐색해 interview-brief 를 만든다. Phase 1 은 seed 가 확정한 것을 불필요하게 다시 묻지 않되, 추론·외부·열린 항목과 새 근거로 흔들린 항목은 재검증한다. 지금 seed 계약은 태그 없는 산문이라 그 구분이 파일에 없다. 사용자는 seed 에 가벼운 구조를 넣는 쪽을 골랐고 확인했다 — 이번 사이클 범위 안이되 무게중심은 interview 다. Phase 0 추가와 interview 보강이 하나의 거대한 책임으로 섞이지 않게 두 단계의 경계와 handoff 계약도 검증하라. Phase 0 파일은 필요하면 고쳐도 된다.
  >
  > Phase 0 에 붙는 새 요구가 하나 있고, 이것도 이번 사이클 범위 안이다. Phase 0 이 워크트리를 만들어 거기서 시작하고, 인터뷰 자료(예: audit, seed)부터 그 브랜치에 커밋하고, 브랜치명을 적절히 정한다 — 사용자 근거는 «대부분 a와 같을거라»(a = 한 브랜치에서 분석→설계→구현)이고, «superpowers 같이»라고 했다. 가능하면 하니스 native 워크트리 도구를 우선한다 — 사용자는 native 가 세션을 워크트리에 고정한다는 대가를 알고 그쪽을 골랐다(확인됨). 다만 사용자가 앞서 말한 «세션에 워크트리가 고정되지는 않게»가 정확히 무엇을 뜻했는지는 확인되지 않았다. Phase 0 관찰: 미커밋 파일은 워크트리에서 보이지 않으므로 Phase 1 이 워크트리에서 시작하려면 audit 이 먼저 그 브랜치에 커밋돼 있어야 하고, native 로 들어가면 브랜치가 worktree 접두어로 나오며 격리 세션의 git 가드가 복합 명령을 막는다. 생성 시점은 열려 있다(예: 첫 라운드, 압축 직후).
  >
  > 한 브랜치에서 원인 분석, 설계, 계획, 구현까지 간다(사용자 확인). Phase 0 관찰: 같은 리포에 steelman 관련 이름의 형제 워크트리가 함께 돌고 있다(다른 세션이 쓰는 중). 겹치면 어떻게 할지는 정해진 바 없다.
